# CloseMeansExit 0.2.1 验证记录

日期：2026-10-31。系统：Windows 11 x64（10.0.26200）。构建工具：.NET SDK 10.0.403。

## 已确认的问题与修复

0.2.0 的只读进程树核验也会拒绝 Windows 目录内的后代程序。桌面应用启动 cmd/conhost 等辅助进程时，探测返回 Reliable=false，候选被取消；未启用黑名单的候选又没有取消日志，因此可能表现为关窗后完全没有提醒。

已对同一个正在运行的 ChatGPT/Codex 根进程使用原版与修复版适配器作只读对照：原版 Reliable=false，修复版 Reliable=true；两者都报告仍有可见窗口。没有关闭或结束该真实应用。这验证了核验路径，不能代替真实关窗验收。

修复后，能够确认身份、父子关系及相同会话的系统后代参与只读窗口保护；实际结束集合仍拒绝系统程序及工具自身。仅结束主进程时，也必须检查这些后代的可见窗口。

## 已实际通过

- Release 构建：零警告、零错误。
- 核心策略、身份、路径、配置与队列：190 条断言。
- Windows 原生检查：可见窗口、最小化、多窗口、保存提示、子进程窗口、PID/创建时间/路径及自身保护。
- Windows 系统辅助进程：不阻断只读驻留发现；启用“包含子进程”时仍拒绝结束含受保护成员的进程树。
- 专用夹具的真实轮询发现 → 右下角卡片 → “加入黑名单”按钮 → 原子保存并重新加载规则 → 当前实例保留 → 下一次强关闭信号对应实例结束。
- 提醒内容、暂不处理、保存失败后重试与队列数量等卡片自动检查。

链路测试在临时目录使用独立配置，所有结束目标均为该次测试创建的专用进程。后续强关闭信号通过协调器注入，没有模拟用户的实体鼠标或键盘。

## 测试夹具修正

旧冒烟向 WinForms 夹具发送裸 WM_CLOSE，其关闭原因会使夹具整体退出，误报“第二窗口未被保护”。现使用 WM_SYSCOMMAND/SC_CLOSE 模拟用户关闭，并检查主窗仅隐藏。此项失败不能作为生产代码多窗口保护失效的证据。

链路测试使用独立的 WinForms 消息循环，保证异步卡片回到测试 UI 线程。
